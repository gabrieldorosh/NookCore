This branch is a development checkpoint. It is separate from the current games candidate and stays disabled by default pending the owner client steering check. The isolated Paper 26.3 adapter and clean restart proof is recorded below; no production data was read.

`travel.lifetime-milestones.enabled` defaults to `false` in `config.yml`. The two configurable goals are `road-mount-blocks: 1000` and `rail-blocks: 1000`. Definitions are installed from the separate `travel-advancements.yml`; existing advancement and game catalogues are preserved. IDs are `nikosnook:travel/a_familiar_road` and `nikosnook:travel/on_the_rails`, with permanent `complete` criteria. There are no currency rewards or reward-map edits. If goals change, edit the descriptions separately to match.

The tracker samples every five ticks and counts horizontal distance only for visible Survival players in an Overworld environment. Hidden staff and vanished players are excluded. Road mounts use the existing configured GroundedTravel mount/material lists and collision tops, with complete collision-top coverage across the actual mount footprint, including partial-block sub-shapes. The first seated player must be on a tamed, saddled mount, grounded and outside water. Rear camel passengers, unsupported mounts and empty carts cannot count. Rail travel requires an occupied rideable cart close to the rail shape and height along its sampled route, with collision support beneath the rail. The API has no direct `isOnRails` getter in this dependency. Curve chords and transitions between slope blocks may undercount. Mixed-height stair footprints are deliberately rejected, so a horse can cross stairs without receiving mileage there. Neither movement speed nor jump strength is an achievement measurement.

World, vehicle, category, mode and mount changes break continuity. Player/vehicle teleports, respawns, deaths, dismounts, reconnects and restarts discard connectors. Large movement, non-finite/out-of-range coordinates, gaps over ten ticks or one second, and speeds above the bounded sampling envelope are discarded. Block checks inspect loaded chunks only and never generate/load terrain. Counters retain millimetres and fractional sample carry; no previous position is persisted.

Distance loads and saves use a background writer and narrow synchronized NookStore methods. A transaction contains at most 64 absolute, monotonic snapshots; repeating a minute/quit/shutdown save cannot add the same distance twice. Normal flushes run once per minute, plus quit and shutdown. Crossing an uncommitted goal queues one bounded immediate asynchronous snapshot; the existing in-flight guard prevents duplicate threshold writes. Grants follow durable acknowledgement on a subsequent sample. Shutdown is idempotent. A crash can lose the unflushed fraction of that minute. Shutdown waits up to ten seconds for queued saves and logs failures. The shared SQLite transaction boundary can briefly serialize other store work during a small batch; there is no per-sample database query or write. This assumes one tracker owns a player's counters in one server process.

Milestones are attempted only after a threshold is durably saved and the player is eligible. Minecraft's saved criterion makes retries after reconnect/restart idempotent; an already earned criterion does not create a new toast or celebration. Cosmetic failure does not alter money or pause games, shops or quests.

Before enabling in any owner fixture, test real player steering on full blocks, dirt paths, permitted slabs/stairs and rail curves/slopes; rear-seat/empty-vehicle exclusions; all hidden-staff transitions; unloaded boundaries; small and large player/vehicle teleports; quit/restart while a save is queued; both threshold crossings; and unchanged balances/ledger. Verify that an earned criterion is not announced or celebrated again after restart. There is deliberately no server-launch helper in this checkpoint.

API checked: installed Paper 26.2 build126 signatures (`Entity.getPassengers`, `AbstractHorse.getInventory`, `Entity.getBoundingBox`, minecart and teleport APIs), plus [Paper entity documentation](https://jd.papermc.io/paper/26.2/org/bukkit/entity/Entity.html). ## Paper 26.3 validation — 4 November 2026

Forty-one focused tests passed: 19 counter/threshold tests, three store tests and 19 catalogue tests. `src/test/probes/run_travel_milestone_checks.py` prepares only a fresh generated loopback fixture at port 25622 and runs two clean server processes. It reuses verified cached server libraries and plugin candidates, never production configuration, worlds, databases or player lists.

The probe uses an unregistered server-backed synthetic player with an in-memory packet listener, a real tamed/saddled first-seat horse, real camel seats and an occupied rideable cart. It invokes the production per-player sampling path with controlled entity positions and clocks. The 99 checks cover exact full-block/path/slab collision tops; complete footprint and unsupported stair-half rejection; rail support, hover/off-track rejection, occupied curves/slopes; real water state; hidden staff/vanish/visibility, modes, other dimension eligibility, empty vehicles/rear seat; teleport/dismount/respawn/world events; delayed/large samples; and unloaded lookups without terrain generation.

Both local-only goals are 20 blocks. Each grants exactly one advancement announcement and one invocation of the real celebration after a durable save. The fixture starts with one zero-value joining ledger record; travel adds no record and changes no balance. A quit save queued behind an occupied writer followed by immediate close preserves exact totals (road 22,000 mm, rail 22,024 mm). A full process restart reloads both Minecraft criteria and exact counters without a connector, duplicate award or celebration. Repeated close is safe.

These are adapter/lifecycle checks, not a real client steering test or hard-crash guarantee. Actual riding over stairs and curve/slope block transitions can undercount conservatively; no unsupported distance is intentionally credited. Original 1,000-block proposals and default-off production settings remain unchanged. The combined candidate still needs its own regression and owner course check.
